10/**
11 * The PHP half of the staging command mutex.
12 *
13 * Only ONE staging operation (create, clone, destroy, a legacy deploy, or a stepped content deploy)
14 * may run against a site at a time: they all move, rsync, `rm -rf` and rename the same production and
15 * staging trees, so two at once can delete files out from under each other and promote a half-built
16 * tree over live production. lib/.staging's `lock_check` is what enforces that, and this class is how
17 * PHP takes part in the same lock.
18 *
19 * ## Why a file, and not the WordPress transient this used to be
20 *
21 * lib/.staging runs WP-CLI with the object-cache drop-in skipped (see the NFD_WP_EXEC comment there),
22 * so `wp_using_ext_object_cache()` is false inside the script while it is true for this request.
23 * Anything the two sides share therefore cannot live anywhere that moves with the object cache. A
24 * transient does: bash wrote it to the database as an option while a persistent cache in front of
25 * `get_transient()` here would answer from a stale (or absent) cached copy. Worse, the lock belongs to
26 * PRODUCTION's install, and a deploy is driven from the STAGING install, whose `$wpdb` points at a
27 * different table prefix -- so a naive `get_transient()` here would read the wrong table entirely and
28 * see no lock at all. A plain file under production's `nfd-private` has neither problem: both sides
29 * address it by absolute path, there is no cache and no prefix, and `nfd-private/.htaccess` (written
30 * by lib/.staging's `log`) already denies it to the web.
31 *
32 * ## Format
33 *
34 * One line: `active:<REFRESHED_AT>:<TOKEN>:<PID>`
35 *
36 *   - REFRESHED_AT -- unix seconds, rewritten on every refresh (NOT the original acquire time).
37 *   - TOKEN        -- opaque `[A-Za-z0-9]{1,64}` identifying the operation holding the lock. A stepped
38 *                     content deploy uses its per-job token (ContentCopyController), so each of its
39 *                     bash bookends re-presents the same token and refreshes the lock it already owns
40 *                     instead of blocking on it. Other commands get a random one from bash.
41 *   - PID          -- the bash process holding the lock, or 0 when no single process does (a stepped
42 *                     job between bursts, which this class refreshes).
43 *
44 * ## Division of labour
45 *
46 * bash is the authority: `lock_check` is the only thing that ACQUIRES or STEALS the lock, and it alone
47 * decides a holder is dead (TTL plus a `kill -0` liveness test on PID). This class only ever READS the
48 * lock, or REFRESHES one that already carries our own token. It never creates, steals or releases one,
49 * so it cannot hand two operations the same mutex.

339     *

341     *   - nothing is running under it. Pid 0, which only refresh() writes, means no bash verb has run
342     *     since the last copy burst. A recorded pid means a verb DID run, and it may be an orphan
343     *     still working -- a killed request leaves setup's `rm -rf` running under this same token --
344     *     so that lock may only be freed once its holder is positively gone. An answer of "cannot
345     *     tell" counts as still running: the cost of being wrong is waiting out the TTL, where the
346     *     cost of the opposite default is freeing the mutex under a live `rm -rf`;
347     *   - it is comfortably within the TTL (by RELEASE_MARGIN), so lib/.staging may not concurrently
348     *     decide it is abandoned and claim it. That is what makes deleting by path safe: a lock
349     *     nobody may steal right now cannot turn into somebody else's between the check and the
350     *     unlink. For a lock already at or past the TTL there is nothing to gain anyway -- it no
351     *     longer blocks anyone.
352     *
353     * Testing liveness rather than insisting on pid 0 is what makes this useful on the path that
354     * actually matters. Restarting after a setup verb outlived its request -- which the UI does by
355     * itself when the first poll times out -- leaves a lock carrying that verb's pid, and refusing it
356     * on the pid alone meant the retry could not free it, could no longer even name its token once
357     * the state file went, and the site refused every staging operation for the full half hour.
358     *
359     * @param string $token Our token.
360     *
361     * @return bool True when a lock was removed.
362     */
363    public function releaseIfOurs( $token ) {
364        if ( ! $this->isValidToken( $token ) ) {
365            return false;
366        }
367
368        $lock = $this->read();
369        if ( null === $lock || $lock['token'] !== $token ) {

371        }
